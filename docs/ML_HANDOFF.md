# 인수인계 — 실측 배차 예측 모델로 시뮬레이터를 전 노선에 확장하기

이 문서 하나만 읽고 작업을 시작할 수 있게 썼다. 이전 대화 맥락은 필요 없다.

---

## 1. 이 프로젝트가 무엇인가

천안시 시내버스의 **정책 시뮬레이터**다. "910번에 버스를 한 대 넣으면 배차·
대기시간·이용객·비용이 어떻게 바뀌는가"에 답한다. 본체는 `src/simulate.py`.

모델은 두 층이다.

| 층 | 식 | 근거 |
|---|---|---|
| 1층 공급 | `h = T / N` | 실측. 항등식이라 추정이 없다 |
| 2층 수요 | `Q′ = Q × (h/h′)^e` | 이용량 Q 는 교통카드 실측, 계수 e 는 문헌값 0.40 |

- `h` 배차간격(분), `T` 한 바퀴 소요시간(분), `N` 투입 대수
- `Q` 하루 이용량(통행), `e` 빈도탄력성

1층에 들어가는 `T`와 `h`는 **공공데이터포털 실시간 버스위치를 60초 간격으로
3주간 받아 직접 잰 값**이다. 소급 수집이 안 되므로 이 기간의 기록은 이것뿐이다.

---

## 2. 무엇이 문제인가

**실측 배차가 22개 노선에만 있다.** 천안시 시내버스는 265개 노선이다.

수집기가 노선마다 다른 주기로 돌았다. 정밀 수집(60초)한 노선은 배차를 잴 만큼
표본이 두텁지만, 나머지는 10분 주기라 같은 정류장을 연속으로 지나간 두 운행을
잡아내기에 성기다. 그래서 `data/processed/headway_by_route.csv` 에 실측값이
있는 노선이 22개뿐이고, 시뮬레이터도 그 노선만 다룬다.

발표 자료에도 "실측이 있는 노선에 한정된다"고 한계로 적어 두었다.

---

## 3. 무엇을 만들 것인가

**노선 특성으로 실측 배차를 예측하는 모델.** 그것으로 나머지 243개 노선의
배차를 채워 넣어 시뮬레이터를 전 노선에 돌린다.

```
입력   노선 특성 (정류장 수, 노선 길이, 공표 배차, 이용량, 민원 …)
        ↓
모델   실측 배차 중앙값 ĥ  (그리고 가능하면 P90)
        ↓
출력   243개 노선의 h 추정치 → simulate.py 가 전 노선을 다룰 수 있게 된다
```

학습 표본은 **실측이 있는 22개 노선**이다. 이 숫자가 이 작업의 전부이자 위험이다.
4절과 7절을 반드시 읽고 시작할 것.

---

## 4. 먼저 읽을 것 — 이 작업이 실패할 수 있는 이유

**n = 22 다.** 특징을 5개만 넣어도 표본 대비 과하다. 다음을 지켜야 한다.

- **특징은 3~5개로 제한한다.** 많이 넣을수록 좋아 보이지만 전부 과적합이다
- **교차검증은 LOO(leave-one-out)** 로 한다. 22개에서 train/test 를 나누면
  test 가 4~5개라 성적이 운에 좌우된다
- **기준선을 반드시 함께 낸다.** "공표 배차를 그대로 예측값으로 쓴다"와
  "전체 평균을 예측값으로 쓴다" 둘 다. 모델이 이 둘을 못 이기면 쓸 이유가 없다
- **성적이 안 나오면 버린다.** 7절의 중단 기준을 미리 정해 두었다

과적합된 모델로 243개 노선의 배차를 지어내면, 그 위에 세운 증차 대수와
예산이 전부 허구가 된다. **없는 것보다 틀린 것이 위험하다.**

## 5. 쓸 수 있는 자료

전부 `data/` 아래에 있다. `data/` 는 `.gitignore` 대상이라 저장소에는 없고
작업 머신에만 있다.

### 5-1. 목표값 (y) — `data/processed/headway_by_route.csv`

`src/build_headway.py` 가 만든다. 노선 22개에 실측값이 있다.

| 열 | 뜻 |
|---|---|
| `routeid` / `routeno` | 노선 식별자 / 번호. **상·하행이 다른 routeid 로 갈라져 있다** |
| `official_min` | 공표 배차(분). TAGO `intervaltime`. 값이 못 믿을 노선은 비어 있다 |
| `median_day_min` | **평상시(07~21시) 실측 배차 중앙값 — 이것이 y 다** |
| `p90_day_min` | 평상시 P90. 둘째 목표값 후보 |
| `median_min` / `p90_min` | 전 시간대. 심야가 섞여 과장되므로 쓰지 말 것 |
| `n_headway` | 배차 사건 표본 수. 가중치로 쓸 수 있다 |
| `cv`, `iqr_min`, `bunching_rate_obs` | 흩어진 정도 |

**주의 두 가지.**

1. `routeno` 기준으로 합쳐야 한다. 상·하행이 별도 행이라 910번이 두 줄
   나온다. `n_headway` 가 큰 쪽을 대표로 쓴다 (`src/make_figures.py` 의
   `by_route()` 가 그렇게 한다)
2. `median_day_min` 이 비어 있으면 `median_min` 으로 떨어지게 되어 있는
   옛 CSV 가 있을 수 있다. 헤더를 먼저 확인할 것

### 5-2. 특징 후보 (X)

| 자료 | 파일 | 뽑을 수 있는 것 |
|---|---|---|
| 노선 정류장 | `data/route_stops.csv` | 정류장 수, 최대 `nodeord`(노선 길이) |
| 노선 상세 | `data/cheonan_routes_detail.csv` | 공표 배차, 첫차·막차, 운행시간대 길이 |
| 통과 사건 | `data/interim/stop_events.csv` | **한 바퀴 소요시간 T** — `simulate.load_trip_minutes()` 를 그대로 부를 것 |
| 교통카드 이용량 | `data/ridership/route_20260801_20260814.csv` | 하루 평균 이용량, 시간대 분포 |
| 민원 | `data/processed/complaints_by_route.csv` | 노선별 민원 수, 결행·무정차 비율 |

**`T` 는 반드시 `simulate.py` 의 함수를 쓸 것.** 그냥 첫 통과~마지막 통과를
재면 60초 주기가 못 본 앞뒤가 잘려 T 가 짧게 나온다. `simulate.load_trip_minutes()`
는 관측한 `nodeord` 구간을 노선 전 구간으로 펴는 보정이 들어 있다.

```python
import sys; sys.path.insert(0, "src")
from simulate import load_trip_minutes, load_ridership, norm_route
T = load_trip_minutes()          # {노선번호: 분}
Q = load_ridership()             # {노선번호: 하루 통행}
```

**민원은 특징으로 쓰지 말 것.** `src/analyze.py` 가 이미 검증했고 기각됐다.
민원 건수와 실측 배차의 순위상관은 2026년 자료로 ρ = +0.03(중앙값),
−0.01(P90) 로 사실상 무상관이다. 넣어도 잡음만 는다. 이 검증 실패는 발표
자료 안에 그대로 실려 있으니, 여기서 민원을 슬쩍 되살리면 앞뒤가 안 맞는다.

### 5-3. 노선 번호 맞추기

교통카드 자료는 `10(상)` 처럼 방향이 붙어 온다. `simulate.norm_route()` 로
정규화해야 TAGO 쪽 `10` 과 붙는다.

## 6. 설계

### 6-1. 특징 (3~5개만)

우선순위 순으로. 위에서부터 넣어 보고 성적이 안 오르면 멈춘다.

1. **`official_min`** — 공표 배차. 시가 계획한 값이라 실측과 가장 강하게
   붙을 것이다. 이것 하나만으로도 상당히 갈 수 있다
2. **`trip_min`** — 한 바퀴 소요시간. 긴 노선일수록 배차가 벌어진다
3. **`log(daily_riders)`** — 이용량. 수요 많은 노선에 버스를 더 넣으므로
   배차가 짧다. **인과가 아니라 상관이다.** 이 모델은 인과 추론이 아니라
   결측 보간이므로 써도 된다. 다만 그 성격을 코드 주석과 결과 문서에 적을 것
4. **정류장 수** — `trip_min` 과 겹칠 가능성이 크다. 상관을 먼저 볼 것
5. **운행시간대 길이(첫차~막차)** — 짧게 운행하는 노선은 배차도 다르다

### 6-2. 모델

**선형회귀부터.** `y = log(median_day_min)` 를 로그로 두면 배차가 양수로만
나오고 비율 오차를 재게 된다.

```
log(h) ~ log(official) + log(T) + log(Q)
```

n=22 에 GBM·랜덤포레스트를 쓰면 거의 확실히 과적합한다. 선형이 기준선을
못 이기면 비선형으로 바꿔도 못 이긴다. 굳이 시도하려면 **Ridge 회귀**
(정규화 강도를 LOO 로 고름) 정도까지다.

외부 패키지를 쓸 수 있으면 `scikit-learn` 이 편하다. 이 저장소는 지금까지
표준 라이브러리만으로 돌아가지만, 이 파일 하나는 예외로 둬도 된다.
다만 **`requirements.txt` 에 적고, 없으면 안내하고 멈추게** 할 것.

### 6-3. 검증 — 이것이 본 작업이다

```
LOO 교차검증 (22번 반복: 1개를 빼고 21개로 학습, 뺀 것을 맞힌다)

지표   MAE(분), MAPE(%), 그리고 기준선 대비 개선률
기준선 A   공표 배차를 그대로 예측값으로  ← 이길 수 있어야 의미가 있다
기준선 B   22개 실측의 중앙값을 모두에 적용  ← 최소한 이것보다는 나아야 한다
```

예측 대 실측 산점도를 그려 어느 노선에서 크게 틀리는지 볼 것.
`src/make_figures.py` 가 외부 패키지 없이 SVG 를 그리는 방식이라 참고가 된다.

### 6-4. 시뮬레이터에 붙이기

성적이 통과하면, `data/processed/headway_predicted.csv` 를 내고
`simulate.load_routes()` 가 실측이 없는 노선에 한해 그것을 쓰게 한다.

**예측값으로 채운 노선은 반드시 표시할 것.** 출력에 `source` 열
(`measured` / `predicted`)을 넣고, 화면에도 예측 노선임을 적는다. 실측과
예측이 섞인 표를 근거로 예산을 논하는 것이 이 작업의 최대 위험이다.

## 7. 중단 기준 — 미리 정해 둔다

다음 중 하나라도 해당하면 **모델을 버리고 지금 상태(22개 노선)로 남긴다.**

- LOO MAE 가 기준선 A(공표 배차 그대로)보다 나쁘다
- MAPE 가 25% 를 넘는다 — 배차 40분을 30~50분으로밖에 못 맞힌다는 뜻이고,
  그 위에서 계산한 증차 대수는 쓸 수 없다
- 특징을 하나 빼고 넣을 때마다 계수 부호가 뒤집힌다 — 표본이 얇다는 신호다

**버리는 것도 결과다.** "n=22 로는 전 노선 확장이 안 된다, 정밀 수집을 넓히는
것이 선행 조건이다" 는 발표에 쓸 수 있는 결론이다. 억지로 살리지 말 것.
