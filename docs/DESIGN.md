# 천안 시내버스 데이터 — 분석·모델 설계

> 2026년 천안시 AI·데이터 기반 정책 아이디어 경진대회 출품용
> 작성 기준: 2026-08-19 (수집 20일차)

이 문서는 **지금까지 수집한 데이터로 무엇을 어떻게 만들 것인가**를 정리한다.
수집 파이프라인(단계 1~3)은 이미 돌고 있으므로, 그 뒤를 다룬다.

문서 안에서 두 가지를 구분해 적는다.

- **[확정]** — 코드·데이터로 이미 검증된 사실
- **[제안]** — 아직 구현되지 않은, 이 문서가 제시하는 설계

## 3. 데이터 모델 — 3계층 [제안]

원본을 직접 분석에 쓰면 매번 같은 전처리를 반복하게 된다. 3계층으로 나눈다.

```
data/
  raw/          수집 그대로 (지금의 data/realtime/, route_stops.csv 등)
  interim/      관측을 '사건' 으로 바꾼 것
  processed/    분석·모델이 바로 먹는 테이블
```

### 3.1 raw → interim : 정류장 통과 사건

실시간 데이터 한 행은 "그 순간 이 버스가 이 정류장에 있(었)다"는 **상태**다.
분석에 필요한 건 "이 버스가 이 정류장을 **언제 지나갔는가**"라는 **사건**이다.

**`interim/stop_events.csv`**

| 컬럼 | 설명 |
|---|---|
| `trip_key` | `routeid` + `vehicleno` + 운행회차 |
| `routeid`, `routeno`, `vehicleno` | |
| `nodeord`, `nodeid`, `nodenm` | 정류소 |
| `pass_ts` | 통과 추정 시각 |
| `obs_count` | 같은 정류장이 연속 관측된 횟수 (정차 길이 힌트) |

**변환 규칙**

1. `(routeid, vehicleno)` 로 묶고 `ts` 정렬
2. `nodeord` 가 **같은 값으로 연속**되면 하나의 정류장 체류로 묶는다
   → `pass_ts` 는 그 묶음의 **마지막 관측 시각**(= 출발에 가장 가까움)
3. `nodeord` 가 **감소**하면 회차 → `trip_key` 의 회차 번호를 +1
4. `nodeord` 가 **2 이상 건너뛰면** 그 사이 정류장은 관측 실패로 기록하고 구간 표본에서 제외

> 3번이 중요하다. 같은 차량이 하루에 같은 노선을 여러 번 왕복하므로,
> 회차를 안 나누면 서로 다른 운행의 관측이 한 시계열로 섞인다.

### 3.2 interim → processed : 구간 소요시간

**`processed/segments.csv`** — 이게 모든 분석의 기본 단위다.

| 컬럼 | 설명 |
|---|---|
| `seg_key` | `routeid` + `from_nodeord` (구간 식별자) |
| `from_nodeid`, `to_nodeid`, `from_nodenm`, `to_nodenm` | |
| `depart_ts`, `arrive_ts` | |
| `travel_sec` | 구간 소요시간 |
| `dist_m` | 정류소 좌표 기반 직선거리 (route_stops 에서) |
| `speed_kmh` | `dist_m / travel_sec` |
| `dow`, `hour`, `is_holiday` | 시간 특성 |

**이상치 규칙 [확정 — 실측에 이미 적용]**
`travel_sec` 이 5초 미만이거나 900초를 넘으면 제외. (GPS 튐, 회차 대기, 결측 구간)

### 3.3 파생 테이블

| 테이블 | 단위 | 용도 |
|---|---|---|
| `processed/trips.csv` | 운행 1회 | 전 구간 소요, 정시성 |
| `processed/headway.csv` | 정류장 × 시각 | 실측 배차간격 |
| `processed/baseline.csv` | 구간 × 시간대 | 자유흐름 기준선 |

## 4. 핵심 지표 정의 [제안]

정의를 먼저 못 박아야 산출물 A~D 가 일관된다.

### 4.1 자유흐름 기준선 (free-flow baseline)

지연을 재려면 "막히지 않았을 때 얼마나 걸리는가"가 있어야 한다.

**정의: 구간별 심야(22:00~23:59) 관측의 `travel_sec` 15퍼센타일**

- 혼잡이 없는 시간대라 구간 소요가 곧 도로의 자유흐름에 가깝다
- 최솟값이 아니라 15퍼센타일을 쓰는 이유: 최솟값은 GPS 튐 하나에 좌우된다
- **제약**: 01:00~05:30 은 수집하지 않으므로 심야 표본이 22~23시에 몰린다.
  22시가 두텁고 23시는 막차 시간대라 표본이 얇다.
  → 심야 표본이 30개 미만인 구간은 **동일 노선의 인접 구간 속도로 대체**한다.

### 4.2 지연 (delay)

```
delay_sec   = travel_sec - baseline_sec
delay_ratio = travel_sec / baseline_sec
```

`delay_ratio` 를 주 지표로 쓴다. 구간 길이가 제각각이라 절대 초는 구간 간 비교가 안 된다.

### 4.3 실측 배차간격 (headway)

같은 정류장·같은 노선·같은 방향에서 **연속한 두 운행의 `pass_ts` 차이**.

- 공표 배차(`cheonan_routes_detail.csv` 의 `intervaltime`)와의 괴리가 곧 정책 근거가 된다
- **번칭(bunching)** 지표: `headway` 가 공표값의 30% 미만인 사건의 비율
  = 버스 두 대가 붙어 다니는 현상. 체감 배차 악화의 주범이라 정책 제안에 쓰기 좋다

### 4.4 정시성

첫차·막차 시각(`startvehicletime`, `endvehicletime`)이 있으므로,
**계획 대비 실제 첫차 출발 시각 편차**를 산출한다. 중간 정류장의 계획 시각표는
공개 데이터에 없으므로, 정시성은 "운행 소요시간의 분산"으로 대체 정의한다.

```
정시성 = 1 - (구간 소요시간의 사분위편차 / 중앙값)
```

## 5. 개편 효과 분석(DID) — **설계상 문제가 있다**

### 5.1 지금까지 준비된 것 [확정]

`rank_control_candidates.py` 가 정류소명 공유율로 대조군 후보를 순위화해 두었다.

| 순위 | 노선 | 처치군과 공유율 | 판정 |
|---|---|---|---|
| 1 | 140 | 46.7% | 적합 |
| 2 | 11 | 45.0% | 적합 |
| 3 | 82 | 37.2% | 적합 |
| 4 | 7 | 34.4% | 적합 |
| 5 | 400 | 34.4% | 적합 |

처치 노선별 최적 짝도 나와 있다. `405→402(70.8%)`, `80→11(45.2%)`, `5→3(25.8%)`.

정류소명 기준으로 판정한 건 옳은 선택이었다. nodeid 로 재면 과소평가된다 —
**고유 정류소명 1,405개에 nodeid 가 2,443개**, 62.1%의 정류소명이 nodeid 를
2개 이상 갖는다(상·하행 승강장 분리). 광덕1리는 nodeid 가 7개다.

### 5.2 문제: '개편 전' 데이터가 없다

DID 는 **처치 전후 × 처치/대조** 네 칸이 필요하다.

|  | 개편 전 (~2023.12) | 개편 후 (2024.1~) |
|---|---|---|
| 처치군 (5·405·80·85·88) | **없음** | 2026.7~8 수집분 |
| 대조군 | **없음** | 2026.7~8 수집분 |

우리가 수집한 실시간 데이터는 **2026년 7~8월, 즉 '개편 후' 뿐**이다.
실시간 데이터는 소급 수집이 불가능하므로 2023년 데이터는 지금 만들 수 없다.

정보공개청구로 받기로 한 **개편 전후 노선대응표**는 "어느 노선이 바뀌었는가"를
알려줄 뿐, **개편 전의 운행 실적**은 아니다.

### 5.3 선택지 [제안]

| 안 | 내용 | 실현성 |
|---|---|---|
| **가** | 정보공개청구를 **BIS 운행이력**까지 확대 (2023년 정류장 통과 이력) | 회신 여부·형식 불확실. 받으면 DID 성립 |
| **나** | DID 를 포기하고 **횡단면 비교**로 전환 — 개편 노선 vs 미개편 노선의 현재 성능 차이 | 즉시 가능. 단 인과 주장 불가, "차이가 있다"까지만 |
| **다** | 처치를 다른 것으로 교체 — 수집 기간 내 발생하는 **강우·요일·첨두** 를 처치로 본 DID | 즉시 가능. 개편 평가는 아니지만 방법론은 온전 |

**권장: 나 + 다 를 본선으로 두고, 가는 회신이 오면 추가한다.**

경진대회 출품 기한을 생각하면 회신을 기다리는 데 프로젝트를 걸 수 없다.
**나**로 현황을 진단하고, **다**로 "지연이 무엇에 의해 발생하는가"를 인과적으로
보인 뒤, 그 위에 예측 모델(B·C)을 얹는 구성이 안전하다.

> **다** 안은 기상 데이터가 필요하다. README 의 단계 4(기상청 ASOS 시간자료)가
> 여기에 쓰인다. 아직 미구현이다.

## 6. 예측 모델 [제안]

### 6.1 B. 도착 지연 예측

**문제 정의**: 특정 구간을 특정 시각에 출발하는 버스의 `travel_sec` 예측

- **단위**: `processed/segments.csv` 한 행
- **표본**: 온전한 12일 기준 295,140개 (수집 종료 시점 약 34만 개)
- **분할**: 시간 기반. 앞 70% 학습 / 다음 15% 검증 / 마지막 15% 평가
  (무작위 분할은 같은 운행의 앞뒤 구간이 학습·평가에 갈라져 누수가 난다)

**특징**

| 그룹 | 변수 |
|---|---|
| 시간 | 시각(순환 인코딩), 요일, 공휴일, 첨두 여부 |
| 공간 | 구간 길이, 노선 유형, 구간의 자유흐름 속도, 직전 구간 지연 |
| 운행 | 해당 운행의 누적 지연, 앞차와의 간격 |
| 외생 | 강수량, 기온 (ASOS) |

**모델**: 구배부스팅(LightGBM 등) 을 기준선으로. 표본 수와 특징 성격상
딥러닝보다 유리하고, 특징 중요도가 정책 설명에 그대로 쓰인다.

**평가**: MAE(초), 그리고 "정시 도착(±2분) 적중률".
비교 대상은 **공표 배차 기반 단순 예측**이어야 한다. 그래야 개선폭이 정책 언어가 된다.

### 6.2 C. 정류장 수요 예측

**여기에도 데이터 문제가 있다.** 버스위치 API 는 **승하차 인원을 주지 않는다.**
수집한 데이터로는 "버스가 어디 있었나"만 알 수 있다.

선택지:

| 안 | 내용 |
|---|---|
| **가** | 교통카드 승하차 데이터를 정보공개청구/공공데이터포털에서 확보 |
| **나** | **대리 지표(proxy)로 전환** — 정류장 체류시간을 수요의 대리변수로 사용 |

**나**가 지금 데이터로 가능하다. `obs_count`(같은 정류장 연속 관측 횟수)가
정차 시간을 반영하고, 정차 시간은 승하차 인원에 비례한다. 60초 주기라 해상도가
거칠지만, **정류장 간 상대 비교**로는 쓸 수 있다.

> 이 경우 산출물 이름을 "정류장 수요 예측"이 아니라
> **"정류장 혼잡도(체류시간) 추정"** 으로 정직하게 바꿔야 한다.

## 7. 모듈 구조 [제안]

기존 `src/` 는 수집 스크립트가 평평하게 쌓여 있다. 분석이 붙으면 섞인다.

```
src/
  config.py
  collect/                    # 기존 (이동만)
    fetch_routes.py
    fetch_route_detail.py
    fetch_route_stops.py
    collect_realtime.py
    fetch_weather.py          # 신규: ASOS
  build/                      # raw -> interim -> processed
    build_stop_events.py      # 3.1
    build_segments.py         # 3.2
    build_trips.py
    build_headway.py
    build_baseline.py         # 4.1
  analyze/
    diagnose.py               # 산출물 A
    compare_routes.py         # 5.3 나안
    did_weather.py            # 5.3 다안
  model/
    features.py
    train_delay.py            # 산출물 B
    estimate_dwell.py         # 산출물 C
  report/
    make_figures.py
    make_report.py
  check_health.py             # 운영 (유지)
```

**원칙**

- `build/` 는 **멱등**하게. 다시 돌리면 같은 결과가 나와야 하고, 이미 만든 날짜는 건너뛴다
- `analyze/`·`model/` 은 `processed/` 만 읽는다. raw 를 직접 읽지 않는다
- 지금까지처럼 **표준 라이브러리 우선**이되, 모델링 단계는 pandas·LightGBM 을 허용한다
  (수집기만은 계속 의존성 0 을 유지 — 3주 무인 운영의 안정성이 그것에 기대고 있다)

수집이 끝나기(8/21)를 기다릴 필요가 없는 것부터 한다.

| 순서 | 작업 | 선행 조건 | 비고 |

## 10. 미해결 사항

정리하면, **데이터가 아니라 설계 쪽에 남은 결정이 둘**이다.

1. **DID 의 '개편 전' 데이터를 어떻게 할 것인가** (5.3)
   → 권장: 나+다 로 본선 구성, 정보공개청구는 병행
2. **승하차 데이터 없이 '수요'를 어떻게 정의할 것인가** (6.2)
   → 권장: 체류시간 대리지표로 전환하고 산출물 이름을 정직하게 조정

둘 다 "데이터를 더 모으면 해결"되는 문제가 아니라 **지금 결정해야 하는 문제**다.
수집은 8/21까지 알아서 돌아가므로, 그 사이에 이 둘을 정하는 것이 가장 급하다.
