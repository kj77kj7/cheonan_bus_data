# 천안 시내버스 데이터 — 분석·모델 설계

> 2026년 천안시 AI·데이터 기반 정책 아이디어 경진대회 출품용
> 개정: 2026-08-26 (STCIS 승하차 확보, DID 폐기)

**[확정]** 은 코드·데이터로 검증된 사실, **[제안]** 은 아직 구현되지 않은 설계다.

---

## 1. 무엇을 만드는가

**배차간격을 줄이거나 노선을 조정하면 이용객이 얼마나 늘어나는가**를 추정하고,
그 추정치로 개선 시나리오별 이용률 증가를 예측한다.

천안시는 대중교통 분담률이 떨어지고 자가용이 늘고 있다. 원인으로 지목되는 것이
구도심의 노선 부족과 긴 배차인데, **"배차를 몇 분으로 줄이면 몇 명이 더 타는가"를
숫자로 답한 자료가 없다.** 그 자리를 메우는 것이 이 프로젝트다.

### 1.1 이전 설계에서 바뀐 것

초기 문서는 **버스 도착 지연 예측**을 본체로 잡았다. 지연은 데이터가 이미 있어서
바로 만들 수 있었지만, "버스가 얼마나 늦는가"는 **왜 사람들이 버스를 안 타는가**에
직접 답하지 않는다. 정책 제안으로 이어지는 것은 이용률 쪽이다.

지연 예측은 버리지 않는다. **정시성·번칭이 서비스 품질 변수로 이용률 모형에
들어간다.** 본체가 아니라 투입으로 자리를 옮겼을 뿐이다.

## 3. 개편 효과 DID 를 폐기한다 [확정]

초기 설계는 2024-01-27 노선 개편을 처치로 삼는 이중차분(DID)을 본체에 두었다.
`rank_control_candidates.py` 가 대조군 후보까지 뽑아 둔 상태였다.

**성립하지 않는다.** DID 는 처치 전후 × 처치/대조 네 칸이 필요한데,

|  | 개편 전 (~2024-01-26) | 개편 후 |
|---|---|---|
| 이용률 (STCIS) | **없음** — 2024-04 이전 데이터 부재 | 있음 |
| 운행 실적 (자체 수집) | **없음** — 2026-07 부터 | 있음 |

'개편 전' 칸이 어느 쪽으로도 채워지지 않는다. 실시간 데이터는 소급 수집이
불가능하고, STCIS 는 그 시기를 갖고 있지 않다.

정보공개청구로 2023년 BIS 운행이력을 받는 방안이 문서에 있었으나, **BIS 이력은
운행 기록이지 승하차가 아니다.** 받아도 이용률 칸은 여전히 빈다.

→ **4장의 패널 설계로 대체한다.** `rank_control_candidates.py` 의 산출물은
지우지 않는다. 노선 유사도는 다른 분석에서 쓸 데가 있다.

## 4. 핵심 모형 — 노선 고정효과 패널 [제안]

### 4.1 문제

"배차가 촘촘한 노선일수록 이용객이 많다"를 단순 회귀로 재면 **인과가 뒤집힌다.**
수요가 많으니까 배차를 더 준 것이지, 배차를 줘서 수요가 는 것이 아닐 수 있다.
전형적인 내생성이다.

### 4.2 해법

STCIS 수집 구간은 2024-05 ~ 2026-08, **2년 4개월 패널**이다. 이 사이에도 배차
조정은 여러 차례 있었다. 노선 고정효과를 넣으면 **같은 노선 안에서 배차가 변한
시점**만 비교하게 된다.

```
log(이용량_it) = β·log(배차간격_it) + γ·X_it + α_i + δ_t + ε_it

  i  노선,  t  시점(수집 구간)
  α_i  노선 고정효과   — 그 노선이 원래 인기 노선인지를 흡수한다
  δ_t  시점 고정효과   — 유가·계절·전반적 통행량 추세를 흡수한다
  β    서비스 탄력성   — 이 프로젝트가 구하려는 값
```

**β 가 답이다.** 배차간격이 1% 늘 때 이용량이 몇 % 주는가. 부호는 음수여야 한다.

개편 전후 DID 보다 오히려 낫다. 사건이 하나가 아니라 여러 번이라 추정이 안정적
이고, 대조군을 누구로 잡느냐는 논란이 없다.

> 해외 문헌의 대중교통 서비스 탄력성은 대체로 0.3~0.7 범위로 보고된다. **이 수치는
> 검증되지 않은 기억이므로 그대로 인용하지 말 것.** 국내 연구·KOTI 자료로 재확인
> 하고, 우리 추정치가 그 범위에 드는지는 타당성 점검으로만 쓴다.

### 4.3 통제변수 `X_it`

| 그룹 | 변수 | 출처 |
|---|---|---|
| 서비스 품질 | 실측 배차의 분산, **번칭 발생률**, 구간 소요시간 | 자체 실시간 수집 |
| 노선 특성 | 운행거리, 경유 정류장 수, 운수업체 | `route_stops.csv`, 운수업체 파일 |
| 권역 수요 | 경유 정류장 반경 인구·종사자수 | 통계청 SGIS |
| 시기 | 요일 구성, 공휴일 수, 강수일수 | 특일정보, 기상 ASOS |

**공표 배차와 실측 배차를 함께 넣는 것이 핵심이다.** 시민이 반응하는 것은 실측
쪽이라는 가설을 검증할 수 있고, 검증되면 그 자체가 정책 메시지가 된다 —
"배차표를 고치는 것보다 지키는 것이 먼저다".

단 실측 배차는 2026-07~08 구간에만 있다. 다른 시점은 공표 배차만 쓰고, 실측은
**최근 구간의 단면 분석**으로 따로 다룬다.

### 4.4 반드시 필요한 것 — 배차간격 이력

`β` 를 구하려면 **같은 노선의 배차가 시간에 따라 변한 기록**이 있어야 한다.
지금 있는 `cheonan_routes_detail.csv` 는 2026년 단면 하나뿐이다.

→ **정보공개청구: 2024~2026 노선별 배차간격 변경 이력.** [DATA_SOURCES.md](DATA_SOURCES.md) A-1.
행정 문서라 회신 가능성이 높고, 표 몇 장이면 끝난다.

받지 못하면 β 추정이 불가능하다. 그때의 대안은 6장.

## 5. 데이터 모델 — 3계층 [제안]

```
data/
  raw/          수집 그대로 (realtime/, ridership/, route_stops.csv)
  interim/      관측을 '사건' 으로 바꾼 것
  processed/    분석·모델이 바로 먹는 테이블
```

### 5.1 정류장 통과 사건 — `interim/stop_events.csv`

실시간 한 행은 "그 순간 이 버스가 여기 있다"는 **상태**다. 필요한 것은 "이 버스가
이 정류장을 언제 지났는가"라는 **사건**이다.

| 컬럼 | 설명 |
|---|---|
| `trip_key` | `routeid` + `vehicleno` + 운행회차 |
| `nodeord`, `nodeid`, `nodenm` | 정류소 |
| `pass_ts` | 통과 추정 시각 |
| `obs_count` | 같은 정류장 연속 관측 횟수 (정차 길이 힌트) |

**변환 규칙**

1. `(routeid, vehicleno)` 로 묶고 `ts` 정렬
2. `nodeord` 가 같은 값으로 연속되면 한 정류장 체류로 묶고, `pass_ts` 는 그
   묶음의 **마지막** 관측 시각 (출발에 가장 가깝다)
3. `nodeord` 가 **감소하면 회차** → 회차 번호 +1
4. `nodeord` 가 **2 이상 건너뛰면** 그 사이는 관측 실패로 기록하고 구간 표본에서 제외

> 3번이 중요하다. 같은 차량이 하루에 여러 번 왕복하므로, 회차를 안 나누면 서로
> 다른 운행이 한 시계열로 섞인다.

### 5.2 실측 배차 — `processed/headway.csv`

같은 정류장·같은 노선에서 **연속한 두 운행의 `pass_ts` 차이**.

- 공표 배차(`intervaltime`)와의 괴리가 곧 정책 근거다
- **번칭**: `headway` 가 공표값의 30% 미만인 사건의 비율.
  두 대가 붙어 오고 다음이 한참 안 오는 현상이라 체감 배차 악화의 주범이다

### 5.3 이용률 패널 — `processed/route_panel.csv`

**모형이 직접 먹는 테이블.** 노선 × 시점 한 행.

| 컬럼 | 설명 |
|---|---|
| `route_id`, `route_no` | |
| `period` | 수집 구간 (2024-05, 2024-09, …) |
| `use_cnt_total`, `use_cnt_peak`, `use_cnt_offpeak` | 이용량 |
| `headway_official` | 공표 배차 (그 시점) |
| `headway_actual`, `bunching_rate` | 실측 (2026 구간만) |
| `route_len_km`, `n_stops`, `operator` | 노선 특성 |
| `pop_catchment`, `job_catchment` | 권역 인구·종사자 |
| `rain_days`, `holiday_count` | 시기 |

### 5.4 구간 소요시간 — `processed/segments.csv`

지연 분석용. 이상치 규칙 **[확정]**: `travel_sec` 이 5초 미만이거나 900초 초과면
제외 (GPS 튐, 회차 대기, 결측 구간).

## 6. 배차 이력을 못 받으면 [제안]

β 추정이 막힌다. 차선책 셋을, 강도 순으로.

| 안 | 내용 | 강도 |
|---|---|---|
| **가** | 배차 변경을 **데이터에서 역추정** — 시점별 이용량 급변 구간을 찾아 노선 개편 공지와 대조 | 약함. 순환논리 위험 |
| **나** | 시점 고정효과만 쓰는 **횡단면 + 권역 통제** — 인구·고용을 통제하고 배차 효과 추정 | 중간. 내생성 잔존 |
| **다** | 문헌 탄력성을 **가져다 쓰고** 시나리오 계산에만 집중 | 약함. 우리 추정이 아님 |

**권장: 나를 본선으로, 다는 비교 참고.** 가는 시간이 남을 때.

이 경우 결론 문장을 정직하게 조정한다 — "배차를 줄이면 이용률이 는다"가 아니라
**"배차가 촘촘한 노선이 인구 조건이 같을 때 이용률이 높다"** 까지만 주장한다.

## 7. 시나리오 시뮬레이션 [제안]

β 가 나오면 정책 질문에 숫자로 답할 수 있다.

```
Δ이용량 = 현재이용량 × [ (신배차/현배차)^β - 1 ]
```

| 질문 | 계산 |
|---|---|
| 구도심 A노선 배차를 30분 → 15분 | 위 식에 대입 |
| 신설 노선의 예상 수요 | 경유 정류장 권역 인구·고용으로 유사 노선을 찾아 이전 |
| 우선순위 | Δ이용량 ÷ 증차 비용 순으로 정렬 |

**우선순위 표가 대회 최종 답변에 해당한다.** "이 노선 셋에 버스 N대를 더 넣으면
연 M명이 늘고, 대당 효율이 가장 높다"까지 가는 것이 목표다.

> 신설 노선 수요 추정은 관측 범위 밖 외삽이다. 반드시 **구간 추정치와 함께**
> 제시하고 단일 숫자로 단정하지 않는다.

## 8. 모듈 구조 [제안]

```
src/
  config.py
  collect/
    fetch_routes.py  fetch_route_detail.py  fetch_route_stops.py
    collect_realtime.py
    fetch_ridership.py  fetch_route_ridership.py   # STCIS
    fetch_weather.py                                # 신규: ASOS
  build/
    build_stop_events.py    # 5.1
    build_headway.py        # 5.2
    build_segments.py       # 5.4
    build_route_panel.py    # 5.3  ← 모형 입력
  analyze/
    diagnose.py             # 산출물 A
    estimate_elasticity.py  # 4장  ← 본체
    simulate.py             # 7장
  model/
    train_delay.py          # 구간 소요시간 예측 (보조)
  report/
    make_figures.py
  check_health.py           # 운영
```

**원칙**

- `build/` 는 **멱등**하게. 다시 돌리면 같은 결과, 이미 만든 것은 건너뛴다
- `analyze/`·`model/` 은 `processed/` 만 읽는다. raw 를 직접 읽지 않는다
- **수집기는 표준 라이브러리만** 유지한다. 3주 무인 운영의 안정성이 거기 기대고
  있다. 분석·모델 단계는 pandas·statsmodels·LightGBM 을 허용한다
